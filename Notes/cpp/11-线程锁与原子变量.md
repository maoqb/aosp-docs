# 线程、锁与原子变量

并发问题并不是“两个线程刚好同时执行同一行”这么简单。真正需要保证的是：哪些状态作为一个整体变化，读线程何时能看见写线程的结果，等待者何时被唤醒，以及对象销毁时所有访问是否已经结束。

本篇用 C++17 的有界队列推导 mutex、条件变量和关闭协议，再解释原子变量的发布语义。

## 1. 数据竞争和业务竞态不是一回事

如果两个线程无同步地访问同一普通内存位置，至少一个写入，就可能形成 C++ 数据竞争并导致未定义行为。这里不是仅仅“读到旧值”，编译器可以基于不存在数据竞争的前提优化。

业务竞态范围更广。即便每个变量都是 atomic，“检查库存还有一个”与“扣减库存”如果不是一个完整原子协议，也可能让两个线程都通过检查。

因此同时需要语言层面的同步和业务层面的状态机。

## 2. mutex 建立什么保证

对同一 mutex 的解锁与后来成功加锁之间建立同步关系，使临界区内先前写入按相应规则对后续持锁访问可见。锁还提供互斥，让一组字段作为整体维护不变量。

例如队列需要同时保护 items、closed 和容量相关判断。只对 push_back 加锁，却在锁外读 empty，仍然破坏协议。

mutex 保护数据，不是给某个函数贴“线程安全”标签。所有访问同一共享状态的路径都必须遵守同一规则，包括日志、析构和错误处理分支。

## 3. 三种锁包装各自表达什么

| 包装 | 常见用途 |
| --- | --- |
| lock_guard | 固定作用域内持锁，不需主动解锁 |
| unique_lock | 可移动、可暂时解锁，适合条件变量等待 |
| scoped_lock（C++17） | 同时获取多把锁，利用避免死锁的组合获取机制 |

不要写一个无名字临时包装，然后误以为后续代码还在锁内。锁对象的析构时刻就是解锁时刻，这正是 RAII 规则。

recursive_mutex 允许同线程重复获取，但通常不能替你修复回调观察半完成状态的问题。死锁消失不代表重入安全。

## 4. 条件变量通知不是持久化消息

通知不保存“有一个事件”供将来消费。应保存的是受 mutex 保护的状态，例如队列非空、已关闭。条件变量只让睡眠线程有机会重新检查状态。

正确等待形式：

```cpp
condition.wait(lock, [&] {
    return closed || !items.empty();
});
```

wait 会在等待期间释放锁，返回前重新获取锁。谓词既应对虚假唤醒，也应对“被唤醒后，别的消费者先取走元素”的真实竞争。

若仅写 if(empty) wait 而不循环检查，醒来后可能访问空队列。

## 5. 完整示例：有界阻塞队列

该队列定义了一个明确关闭策略：close 后不再接受新元素，但消费者仍可取完已入队元素；关闭且队列为空时，pop 返回 nullopt。

```cpp title="blocking_queue.cpp"
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <iostream>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <thread>

class BlockingQueue {
public:
    explicit BlockingQueue(std::size_t capacity) : capacity_(capacity) {
        if (capacity == 0) {
            throw std::invalid_argument("capacity must be positive");
        }
    }

    bool push(int value) {
        std::unique_lock<std::mutex> lock(mutex_);
        notFull_.wait(lock, [this] {
            return closed_ || items_.size() < capacity_;
        });

        if (closed_) {
            return false;
        }

        items_.push_back(value);
        lock.unlock();
        notEmpty_.notify_one();
        return true;
    }

    std::optional<int> pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        notEmpty_.wait(lock, [this] {
            return closed_ || !items_.empty();
        });

        if (items_.empty()) {
            return std::nullopt;
        }

        int value = items_.front();
        items_.pop_front();
        lock.unlock();
        notFull_.notify_one();
        return value;
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            closed_ = true;
        }
        notEmpty_.notify_all();
        notFull_.notify_all();
    }

private:
    const std::size_t capacity_;
    std::mutex mutex_;
    std::condition_variable notEmpty_;
    std::condition_variable notFull_;
    std::deque<int> items_;
    bool closed_ = false;
};

int main() {
    BlockingQueue queue(2);

    std::thread producer([&queue] {
        for (int value : {1, 2, 3}) {
            if (!queue.push(value)) {
                break;
            }
        }
        queue.close();
    });

    int total = 0;
    while (auto value = queue.pop()) {
        total += *value;
    }

    producer.join();
    std::cout << "total=" << total << '\n';
    std::cout << std::boolalpha << "accepts after close=" << queue.push(4) << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -pthread blocking_queue.cpp -o blocking_queue
./blocking_queue
```

输出为 total=6 和 accepts after close=false。

本示例是启用异常的主机程序。Android 禁用异常模块应将容量校验改为适用的构造前检查或工厂错误结果；同步协议本身不依赖异常。

## 6. 为什么这个关闭协议不会漏掉等待者

消费者等待“已关闭或非空”，生产者等待“已关闭或有容量”。close 在同一把 mutex 下修改 closed，再通知两组等待者。

如果通知发生在等待之前，等待者之后检查到 closed 就不会睡；如果等待者已释放 mutex 进入等待，notify 会唤醒它。因此关键是状态和检查都使用同一个 mutex，而不是通知必须碰巧发生在某一行之后。

消费者醒来后只有队列为空才结束，保证 close 前接受的元素仍可处理。若业务要求立即丢弃，应明确改变状态机，并在合适锁范围外销毁可能带回调的队列元素。

## 7. 线程对象的寿命也是所有权

std::thread 析构时若仍 joinable，会调用 terminate。线程函数正常返回并不会自动让 thread 包装变成已 join 状态。

示例先 join，再离开 queue 作用域，因此工作线程不再访问已销毁的 mutex 或队列。detach 则放弃等待能力，不会自动延长捕获的 queue 引用寿命。

C++20 jthread 提供自动 join 与停止令牌，但协作停止仍要让阻塞等待有机会退出。换一个线程包装不能代替队列 close 协议。

## 8. 原子变量适合表达单点状态

atomic<int> 的 fetch_add 可以安全更新一个计数，但不会自动保护计数所指向的 vector。对多字段不变量，mutex 往往更直接。

下面的发布示例使用一个原子标志，使普通数据写入在读取时可见：

```cpp title="atomic_publish.cpp"
#include <atomic>
#include <iostream>
#include <thread>

int main() {
    int payload = 0;
    std::atomic<bool> ready{false};

    std::thread publisher([&] {
        payload = 42;
        ready.store(true, std::memory_order_release);
    });

    while (!ready.load(std::memory_order_acquire)) {
        std::this_thread::yield();
    }

    std::cout << payload << '\n';
    publisher.join();
}
```

输出是 42。release 前的 payload 写入，经由读取到该发布值的 acquire，建立到后续 payload 读取的先行发生关系。

如果把标志读写都改 relaxed，在 join 之前读取普通 payload 就失去所需同步，可能产生数据竞争。原子标志自身没撕裂，不等于它旁边的数据可见。

本例用轮询只为显露内存序；真实低频等待通常使用条件变量或平台等待机制，避免无谓占用 CPU。

## 9. relaxed、acquire/release 和 seq_cst

relaxed 提供该原子对象的原子性和修改顺序，但不建立普通关联数据的发布关系。acquire/release 可构造明确的生产消费同步。默认 seq_cst 还提供相应原子操作的全局一致顺序模型，通常更易初学者推理。

不要把这些内存序简单解释为“清 CPU 缓存”。C++ 描述抽象机器的可见性和顺序，编译器再映射到不同 CPU 指令。相同源码在 ARM 和 x86 上可能采用不同屏障实现。

volatile 不提供这些同步保证，它主要处理特定可观察访问语义，不能替代 atomic 或 mutex。

## 10. Binder 为什么放大锁的风险

同步 Binder 调用可能回调当前进程，并出现嵌套事务。若调用方持锁等待远端，远端又回调需要同一把锁的接口，就可能形成环。

```text
服务 A 持锁 → 同步调用 B → B 回调 A → A 回调等待原锁
```

即使只有一条 Binder 工作线程，也可能发生事务重入；“单线程池”不等于“不必考虑回调”。应在调用外部代码前构造一致状态和必要快照，再按设计释放锁。

## 11. 排查并发问题的推理方法

先列出每个共享字段的保护方式，再列读写入口及执行线程，最后检查两条可能交错的路径。锁顺序、回调位置和析构位置必须一起看。

TSan 可帮助找到未同步访问，但不能保证发现所有业务竞态。死锁还需要等待图：哪个线程拿着什么，等待什么，另一方又依赖谁。工具提供具体交错证据，状态模型解释为何该交错不允许。

标准内存模型见 [intro.races](https://eel.is/c++draft/intro.races)，Binder 线程和重入规则参见 [AOSP Handle threads](https://source.android.com/docs/core/architecture/ipc/binder-threading)。
