# AIDL NDK 与系统服务

AIDL 将稳定接口描述生成 Java、C++ 或 NDK Binder 桥接代码。系统服务代码阅读应从注册和接口边界开始，而不是先进入庞大实现类。

## AIDL 生成物

接口定义生成客户端代理、服务端 Stub、transaction code 和 Parcel 序列化逻辑。NDK 后端常见 `ndk::SpAIBinder`、`Bn*`、`I*` 类型；具体命名随后端和平台版本不同，但角色不变：接口、客户端代理、服务端分发、实现类。

## 服务生命周期

Native 服务通常经历：创建实现对象 → 初始化依赖 → 注册到 ServiceManager → 启动/加入 Binder 线程池 → 接收调用。客户端通过 service name 查询 Binder，再转换为接口代理。service name 是跨进程契约的一部分，修改它会影响所有客户端。

## 安全与身份

服务端必须在业务入口检查调用 UID/PID、SELinux 域和权限。不要只在 Java API 层做权限判断；任何能拿到 Binder 的客户端都可能直达 Native 服务。清除/恢复 calling identity 只能在完全理解身份传播语义时使用。

## 阅读方法

选择一个小服务，依次记录：AIDL 文件、生成接口、注册位置、实现类、线程池配置、权限检查和一个具体方法的完整调用链。这样建立的地图可迁移到更复杂的 WMS、媒体或图形服务。

## 易错点

- AIDL 代码生成解决协议，不解决业务线程安全和权限校验。
- 服务注册成功不代表依赖都已就绪，注意 init 顺序。
- 不要在 Binder 回调中做阻塞 IO 或回调未知客户端。
