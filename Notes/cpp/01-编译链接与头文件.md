# 编译、链接与头文件

C++ 项目中，“代码写对了”只解决一部分问题。一个函数还必须在调用处有正确声明、被某个编译单元定义、随目标文件进入链接，最后由运行时加载器找到依赖库。Android 中的 undefined symbol、头文件找不到、改动不生效，经常分别发生在这些不同环节。

本篇用一个完整的多文件程序建立构建模型，再把模型对应到 AOSP 的 Soong 模块。示例使用 C++17；命令可以在安装 GCC 的 Linux 主机运行，Android 产品构建使用所选分支配套的 Clang 工具链。

## 1. 从 Java 的类加载切换到 C++ 的构建模型

Java 的 `import` 让源文件使用另一个类型的名字；它不会把另一个源文件文本复制到当前文件。C++ 的 `#include` 主要由预处理器处理，效果接近在当前位置展开头文件内容。

| 问题 | Java 中常见答案 | C++ 中的答案 |
| --- | --- | --- |
| 编译器如何知道方法签名 | 类信息、源文件或 class 文件 | 当前编译单元中可见的声明 |
| 方法实现在哪里 | 字节码，运行时再解释或编译 | 目标文件或链接库中的机器码 |
| 两个文件如何调用对方 | 符号引用及类加载 | 外部符号的链接与重定位 |
| 类型包名 | package | namespace，但 namespace 不负责加载文件 |
| 程序依赖何时失败 | 可能在类加载或方法解析时 | 编译、链接、装载阶段均可能失败 |

头文件通常不是一个独立运行的东西，也不是一份可直接链接的库。它提供编译器需要的声明；库才提供已编译的实现。

## 2. 一个函数经历哪些步骤

`main.cpp → 预处理后的文本 → 汇编 → main.o → 可执行文件` 是概念上的流水线。现代编译器可能合并步骤，但错误类型仍可以按这条链分析。

预处理负责展开头文件、条件编译和宏；编译负责类型检查、生成中间表示及优化；汇编负责产生目标文件；链接负责解析符号和组织最终产物。动态链接的程序还要在启动时加载共享库。

可以用这些命令观察各阶段：

```bash
g++ -std=c++17 -E main.cpp -o main.ii
g++ -std=c++17 -S main.cpp -o main.s
g++ -std=c++17 -c main.cpp -o main.o
```

`-E` 停在预处理，`-S` 停在汇编文本，`-c` 生成目标文件但不链接。不要把“生成了 .o”当作“整个程序已构建成功”。

## 3. 完整示例：声明和实现分开

将以下三个文件放在同一个目录。

```cpp title="calculator.h"
#ifndef CPP_NOTES_CALCULATOR_H
#define CPP_NOTES_CALCULATOR_H

namespace demo {
int add(int left, int right);
}

#endif
```

```cpp title="calculator.cpp"
#include "calculator.h"

namespace demo {
int add(int left, int right) {
    return left + right;
}
}
```

```cpp title="main.cpp"
#include "calculator.h"

#include <iostream>

int main() {
    std::cout << demo::add(20, 22) << '\n';
}
```

编译运行：

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -c calculator.cpp -o calculator.o
g++ -std=c++17 -Wall -Wextra -Wpedantic -c main.cpp -o main.o
g++ main.o calculator.o -o calculator
./calculator
```

输出为 `42`。编译 `main.cpp` 时，编译器通过头文件知道 `demo::add` 接受两个 int 并返回 int，因而可以生成调用指令；此时它不要求看见函数体。

链接阶段，`main.o` 需要一个外部符号，`calculator.o` 提供这个符号。`nm -C main.o` 中对应项通常标为 `U`，表示未定义引用；`nm -C calculator.o` 中对应项通常标为 `T`，表示代码段中的定义。`-C` 将 C++ 修饰过的符号名解码为可读形式。

由此可以精确解释两种故障：

- 去掉 `main.cpp` 的 include：函数未声明，是编译错误。
- 链接时漏掉 `calculator.o`：声明存在而实现缺席，是链接错误。

仅添加 include 无法解决后一种问题。

## 4. 声明、定义和 ODR

**声明（declaration）**告诉编译器“有这个名字，它是什么类型”；**定义（definition）**还会真正给函数提供函数体、给对象提供存储，或者完整描述一个类。同一个实体可以先后声明多次，但声明的类型必须一致。

```cpp
int add(int, int);          // 函数声明
int add(int a, int b) {     // 函数定义，同时也是声明
    return a + b;
}

extern int request_count;   // 对象声明，本处不定义对象
int request_count = 0;      // 对象定义
extern int retry_count = 0; // 有初始化器，仍然是定义
```

预处理完成后，一个 `.cpp` 连同它展开的头文件构成一个**翻译单元（translation unit）**，也常被宽泛地称为编译单元。每个翻译单元独立编译，所以 `main.cpp` 只要看到了 `add` 的声明就能通过类型检查；真正的定义可以由另一个目标文件提供。

**ODR（One Definition Rule，单一定义规则）**规定同一实体可以有多少个定义。面向日常工程，可以分两层理解：

1. 在同一个翻译单元中，同一个函数、变量、类或模板不能定义两次。头文件被重复展开后产生的重定义，通常在编译阶段就能报出。
2. 在整个程序中，被实际使用的普通非 `inline` 函数或具有外部链接的变量，应当有且仅有一个定义。没有定义通常得到 `undefined reference`，普通定义重复通常得到 `multiple definition`。

这里的“被实际使用”对应标准里的 **odr-use**。简化地说，调用一个函数，或者读取、修改、取地址而需要某个对象真实存在，通常就是 odr-use。某些只参与编译期常量计算、`sizeof` 等不求值场景不一定构成 odr-use，因此不能把它等同于“源码里出现了这个名字”。

ODR 也不是“任何定义在整个程序中都只能写一次”。类定义、模板定义、`inline` 函数，以及 C++17 的 `inline` 变量可以出现在多个翻译单元中——这正是它们通常能够写进头文件的原因。条件是各处定义必须等价，例如 token 序列相同，定义中查找到的名字也指向相同实体。这里的 **token（词法单元）**是编译器识别出的关键字、标识符、字面量、运算符或标点等基本单位。

```cpp title="packet.h"
struct Packet {
#ifdef ENABLE_TRACE
    int trace_id;
#endif
    int payload_size;
};
```

如果 A.cpp 定义了 `ENABLE_TRACE`，B.cpp 没有定义，同一个 `Packet` 会得到两种布局。这违反 ODR，但链接器看到的未必是两个容易比较的普通符号，因而可能完全不报错，最后表现为字段错位、越界或随机崩溃。标准把一部分此类情况规定为“**不要求诊断**”：程序是错误的，但编译器和链接器没有义务发现它。

工程上最稳妥的基线是：

- 普通外部函数和全局变量只在一个 `.cpp` 中定义，在头文件中声明。
- 类、模板和确实需要 header-only 的实现放在头文件，并保证所有翻译单元看到相同定义。
- 不要用随源文件变化的宏改变公共类布局或 `inline` 函数语义；平台、架构条件确有需要时，确保同一个最终程序中的宏配置一致。

## 5. include guard 解决不了重复链接定义

**include guard（头文件保护宏）**只阻止同一个头文件在**一个翻译单元内**被展开多次：第一次包含时定义宏，之后再包含就跳过正文。

```cpp
#ifndef CPP_NOTES_COUNTER_H
#define CPP_NOTES_COUNTER_H

// declarations...

#endif
```

这能阻止 `a.h → b.h → a.h` 之类的包含链再次展开同一头文件，却不会在不同翻译单元之间共享状态；如果 A、B 两个类型都要求先看到对方的完整布局，guard 也不能消除这种设计上的循环依赖。假设 A.cpp 和 B.cpp 都包含下面的头文件：

```cpp title="counter_bad.h"
#ifndef CPP_NOTES_COUNTER_BAD_H
#define CPP_NOTES_COUNTER_BAD_H

int request_count = 0;

int next_request_id() {
    return ++request_count;
}

#endif
```

A.cpp 内只展开一次，B.cpp 内也只展开一次；链接时仍然有两个 `request_count` 和两个 `next_request_id` 定义。guard 完成了自己的工作，错误来自跨翻译单元违反 ODR。

### 5.1 常规修复：头文件声明，源文件定义

```cpp title="counter.h"
#ifndef CPP_NOTES_COUNTER_H
#define CPP_NOTES_COUNTER_H

extern int request_count;
int next_request_id();

#endif
```

```cpp title="counter.cpp"
#include "counter.h"

int request_count = 0;

int next_request_id() {
    return ++request_count;
}
```

所有使用方看到相同声明，只有 `counter.cpp` 产生定义。这也是有共享可变状态时最容易审查的组织方式；多线程访问仍需另行同步。

### 5.2 确实要写在头文件时

函数可以定义为 `inline`，C++17 起变量也可以定义为 `inline`：

```cpp title="counter_inline.h"
#pragma once

inline int request_count = 0;

inline int next_request_id() {
    return ++request_count;
}
```

此处的 `inline` 首先是一种语言和 ODR 语义：允许等价定义出现在多个翻译单元中，并让具有外部链接的 `inline` 实体在程序中表现为同一实体。它**不承诺**编译器一定把函数体展开到调用点；反过来，优化器也可以展开一个没写 `inline` 的函数。类定义内部给出函数体的成员函数隐式具有 `inline` 属性，模板定义也通常需要让实例化它的翻译单元可见。

不要用头文件中的 `static int request_count` “消除”重复定义。命名空间作用域的 `static` 会让每个翻译单元得到一份私有对象：链接错误消失了，但“全程序共用一个计数器”悄悄变成“每个 `.cpp` 各有一个计数器”。只读编译期常量可以写成 `inline constexpr`；如果程序依赖地址唯一性，也要避免无意制造每个翻译单元一份的常量。

`#pragma once` 是 Clang、GCC 等工具链广泛支持的简写，但它不是 C++17 标准中的预处理指令；传统 guard 可移植性最明确。两者解决的层次相同，都不能代替 ODR。无论选择哪种方式，公共头文件还应做到**自包含**：直接包含自己所使用类型的必要头文件，而不是依赖某个调用方碰巧先包含了它们。`.cpp` 首先包含自己的头文件，是暴露这类遗漏的简单办法。

## 6. 前置声明为什么有效

`class Connection;` 是**前置声明（forward declaration）**：它告诉编译器 `Connection` 是一个类名，但尚未给出类体。此时 `Connection` 是**不完整类型（incomplete type）**，编译器不知道它的大小、对齐、基类和成员布局。

关键判断不是“有没有 include”，而是当前操作是否需要完整类型：

| 仅有 `class Connection;` 时 | 是否可行 | 原因 |
| --- | --- | --- |
| 声明 `Connection*`、`Connection&` | 可以 | 指针大小已知，引用也不内嵌对象布局 |
| 声明参数为指针或引用的函数 | 可以 | 只需知道函数签名 |
| 声明按值传入或返回 `Connection` 的函数 | 可以 | 只有声明，不生成传值代码；定义或调用时需要完整类型 |
| 定义 `Connection connection;` 或按值数据成员 | 不可以 | 必须知道对象占多少空间、如何构造和析构 |
| `sizeof(Connection)`、访问 `connection->member` | 不可以 | 必须知道布局或成员集合 |
| `class Client : public Connection` | 不可以 | 派生类布局依赖基类完整定义 |

所以头文件可只暴露借用关系，实现文件再包含完整定义：

```cpp title="client.h"
#pragma once

class Connection;

class Client {
public:
    explicit Client(Connection& connection);
    void send();

private:
    Connection& connection_;
};
```

```cpp title="client.cpp"
#include "client.h"

#include "connection.h"  // send() 要访问 Connection 的成员

Client::Client(Connection& connection) : connection_(connection) {}

void Client::send() {
    connection_.flush();
}
```

这样 `client.h` 的使用方不必因为 `connection.h` 的实现细节变化而全部重新编译。但引用不表达所有权，并且被引用的 `Connection` 必须比 `Client` 活得久；前置声明只减少编译依赖，不负责生命周期安全。

### 6.1 PImpl：把私有布局也移出头文件

**PImpl（pointer to implementation，指向实现的指针）**让公开类只保存一个指向私有实现对象的指针：

```cpp title="widget.h"
#pragma once

#include <memory>

class Widget {
public:
    Widget();
    ~Widget();

    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    Widget(const Widget&) = delete;
    Widget& operator=(const Widget&) = delete;

    void start();

private:
    class Impl;
    std::unique_ptr<Impl> impl_;
};
```

```cpp title="widget.cpp"
#include "widget.h"

#include <memory>

class Widget::Impl {
public:
    void start() { running_ = true; }

private:
    bool running_ = false;
};

Widget::Widget() : impl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;
Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;

void Widget::start() {
    impl_->start();
}
```

`std::unique_ptr<Impl>` 可以作为持有不完整类型的成员，但默认删除器真正执行 `delete` 时必须看到完整的 `Impl`。因此析构函数只在头文件声明，在 `widget.cpp` 看见 `Impl` 定义后再写 `= default`。移动构造和移动赋值也放在 `.cpp`，能避免特殊成员函数的实例化位置再次碰到不完整类型。拷贝操作在这里显式删除，是因为 `unique_ptr` 不可拷贝；需要值语义时，应自行实现深拷贝。

PImpl 有两类收益：私有字段变化不会沿 include 图触发大面积重编译；公开类的布局不再随 `Impl` 的私有字段变化，在常见实现中只保留一个指针大小的成员，从而降低二进制兼容风险。**ABI（Application Binary Interface，应用二进制接口）**是已编译模块之间的二进制契约，包括对象布局、参数如何通过寄存器或栈传递、符号命名、调用约定等。PImpl 只隔离部分对象布局，不能自动保证完整 ABI 稳定：公开函数签名、虚函数表、异常、运行库版本以及跨库内存释放仍可能造成不兼容；它通常还引入一次额外堆分配、一次间接访问和额外样板代码。

## 7. namespace、static、extern 与 extern "C"

这几个语法经常同时出现在头文件里，但处理的是不同问题：

| 概念 | 它回答的问题 | 典型写法 |
| --- | --- | --- |
| 作用域（scope） | 这个名字在源码的哪些位置可见、名字查找会找到谁 | `namespace media { ... }` |
| 链接属性（linkage） | 不同翻译单元里的同名声明是否指向同一实体 | 命名空间作用域的 `static`、普通外部函数 |
| 存储期（storage duration） | 一个对象的存储从何时存在到何时结束 | 函数内 `static` 对象 |
| 语言链接（language linkage） | 按哪种语言约定连接函数名和函数类型 | `extern "C"` |

### 7.1 namespace 管名字，不负责加载文件

`namespace` 控制名字的归属和查找，`demo::add` 与 `other::add` 是不同实体；它不会自动寻找源文件、链接库，也不要求命名空间与目录一一对应。命名空间可以跨多个头文件和源文件继续定义。

不要在公共头文件的命名空间作用域写 `using namespace std;`。头文件会被文本展开，这条指令会把大量候选名字带进每个包含者的名字查找，可能产生歧义或让调用意外绑定到另一个重载。应在接口中写 `std::string` 这样的限定名；局部实现中的短范围 `using` 更容易控制。

匿名命名空间适合 `.cpp` 私有辅助实体：

```cpp
namespace {
constexpr int kMaxRetries = 3;

void logRetry() {
    // 只供当前翻译单元使用
}
}  // namespace
```

其中的名字具有**内部链接（internal linkage）**，即其他翻译单元里的同名实体不是它。相对地，普通命名空间作用域函数通常具有**外部链接（external linkage）**，不同翻译单元中的匹配声明可以指向程序里的同一个实体。

### 7.2 `static` 至少有三种常见含义

`static` 不是“静态库”的开关，它的含义取决于出现位置：

```cpp
static void helper();       // 命名空间作用域：内部链接，仅本翻译单元可见

void handle() {
    static int calls = 0;   // 块作用域：静态存储期，多次调用共享同一对象
    ++calls;
}

class Session {
public:
    inline static int count = 0; // 类静态成员：属于类，不属于某个 Session 对象
};
```

函数内局部 `static` 的名字仍只有块作用域，但对象存活到程序结束；从 C++11 起，它的首次初始化由语言保证线程安全，初始化完成后的读写是否安全仍取决于代码自身的同步。命名空间作用域的私有实现，现代 C++ 通常优先使用匿名命名空间；它也能容纳类型、模板等不能简单套用函数式 `static` 写法的实体。

### 7.3 `extern` 声明不等于 `extern "C"`

单独的 `extern` 是存储类说明符。命名空间作用域下最常见的用途，是声明“定义在别处”的对象：

```cpp title="stats.h"
extern int request_count;
```

```cpp title="stats.cpp"
#include "stats.h"

int request_count = 0;
```

`extern` 不会自动查找或加载某个库；最终仍需把提供定义的目标文件或库加入链接。也不要在头文件里写 `extern int request_count = 0;`，初始化器会让它成为定义。

`extern "C"` 则是**语言链接说明**，常用于 C 与 C++ 的接口边界：

```c title="codec.h"
#ifndef CPP_NOTES_CODEC_H
#define CPP_NOTES_CODEC_H

#ifdef __cplusplus
extern "C" {
#endif

int codec_open(const char* path);
void codec_close(int handle);

#ifdef __cplusplus
}
#endif

#endif
```

`__cplusplus` 只在 C++ 编译器下定义，所以同一头文件也能被 C 编译器读取。C++ 会为重载、命名空间等功能进行**名字修饰（name mangling）**，把函数名和部分类型信息编码进符号名；`extern "C"` 要求使用 C 语言链接，通常可得到 C 工具和 `dlsym` 更容易约定的符号名及调用方式。同名的 C 链接函数不能像普通 C++ 函数那样靠参数类型重载。

但 `extern "C"` 只解决 ABI 的一部分：

- 它不会把函数体改成 C，也不会让 C 编译器理解类、模板或 `std::string`。
- 它不会自动导出 ELF 符号；**ELF** 是 Android/Linux 常用的目标文件、共享库和可执行文件格式。外部链接与 `default`/`hidden` 符号可见性是不同维度，版本脚本和编译选项仍可能隐藏它。
- 它不会统一不同编译器/运行库的类布局、异常实现和内存分配器。稳定边界通常使用定宽整数、字节缓冲区、显式长度和不透明句柄，并明确由哪一侧创建、销毁资源。

JNI 的按名字查找入口常见如下：

```cpp
extern "C" JNIEXPORT jlong JNICALL
Java_com_example_NativeBridge_nativeOpen(JNIEnv* env, jobject thiz) {
    // ...
}
```

这里 `extern "C"` 提供 C 语言链接，`JNIEXPORT` 控制导出可见性，`JNICALL` 表示 JNI 规定的调用约定，它们职责不同。使用 `RegisterNatives` 动态注册时，运行时拿到的是显式传入的函数地址，不要求导出 `Java_...` 名字，但函数签名和生命周期仍必须符合 JNI 约定。

遇到边界问题时，可先用 `nm -C file.o` 查看目标文件的定义与未定义引用，用 `nm -D -C libname.so` 或 `readelf -Ws libname.so` 查看共享库的动态符号表。若“库里明明有函数”却仍找不到，应逐项比较命名空间、参数的 `const`/引用差异、C/C++ 语言链接、符号可见性以及实际装载的 `.so` 版本。

## 8. 静态库和共享库

静态库 `.a` 可理解为目标文件归档，链接器从中抽取所需内容进入最终产物。链接静态库时，传统链接器的参数顺序可能影响符号解析。

共享库 `.so` 通常保留为独立装载单元；最终程序记录依赖，由动态加载器查找并装载。构建时能找到库，不代表目标设备一定装有兼容版本。

分析报错应区分：

| 报错表现 | 优先检查 |
| --- | --- |
| header not found | include 路径、头文件导出、生成步骤 |
| no matching function | 可见签名、const、命名空间、参数类型 |
| undefined reference | 实现是否编译、依赖是否链接、符号是否导出 |
| multiple definition | 头文件定义、重复加入的对象或库 |
| dlopen / cannot locate symbol | 设备上的实际库版本、ABI、运行时依赖 |

## 9. 对应到 Android.bp

下面是 Soong 平台模块的教学示例，需要放在 AOSP 树的合适目录：

```bp
cc_library_shared {
    name: "libcpp_notes_calculator",
    srcs: ["calculator.cpp"],
    export_include_dirs: ["include"],
    cpp_std: "c++17",
}

cc_binary {
    name: "cpp_notes_calculator",
    srcs: ["main.cpp"],
    shared_libs: ["libcpp_notes_calculator"],
    cpp_std: "c++17",
}
```

此布局将 calculator.h 放在 `include/`，其他两个文件在模块目录。库导出的 include 目录让消费者看到接口，`shared_libs` 则建立实现依赖。`header_libs` 只提供头文件相关依赖，本身不提供某个函数的机器码。

读取真实模块时还要追踪 `defaults`、架构条件、生成源码、vendor/product 变体。相同模块名在不同产品配置下可能选择不同源文件，不能只看一处 srcs。

查找定义后，沿最近的 Android.bp 确认模块归属，再查消费者如何依赖它。这个过程能回答“我改的实现到底会不会进入当前镜像”。

## 10. 阅读依据

语言规则以 [WG21 N4659（C++17 工作草案）](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2017/n4659.pdf) 为本篇基线，可重点查阅 §6.1 声明与定义、§6.2 ODR、§6.5 程序与链接、§10.1.6 `inline`、§10.5 语言链接；[当前工作草案的 ODR 条款](https://eel.is/c++draft/basic.def.odr) 便于在线检索，但编号和细节可能已随新标准演进。Android ABI 可查 [Android ABIs](https://developer.android.com/ndk/guides/abis)，跨共享库使用 C++ 运行库的约束可查 [C++ library support](https://developer.android.com/ndk/guides/cpp-support)。Android 模块语义以 [Soong README（Android 16 标签）](https://android.googlesource.com/platform/build/soong/+/refs/tags/android-16.0.0_r4/README.md) 和项目实际构建配置为准。
