# 智能指针与所有权

智能指针解决的是释放责任如何随控制流和对象关系传播。它不会自动推断业务对象应活多久，也不能代替锁。使用之前要先区分独占所有权、共享所有权与借用，这比选择某个模板名字更重要。

本篇讨论标准库 C++17 的 unique_ptr、shared_ptr 和 weak_ptr；Android 的 sp/wp 在第 13 篇单独解释。

## 1. 所有权图决定资源何时消失

假设 Session 保存一个 Connection，Connection 又保存回调。如果两者互相强持有，那么外部放手也不会自动断开这条环。

```mermaid
flowchart LR
    External["外部所有者"] --> Session["Session"]
    Session -->|"强持有"| Connection["Connection"]
    Connection -.->|"反向观察宜用弱引用"| Session
```

画图时必须给边标语义。普通指针边只表示访问通道，未必是强边；强边保持目标存活，弱边只允许在使用前尝试取得强持有。

## 2. unique_ptr：将唯一责任写进接口

unique_ptr 不能复制，可以移动。对象销毁、reset 或被另一个值覆盖时，旧目标由删除器清理。默认删除器使用 delete，数组特化使用对应数组形式。

```cpp
std::unique_ptr<Connection> createConnection();
void installConnection(std::unique_ptr<Connection> connection);
void inspectConnection(const Connection& connection);
```

前两行表达返回和接收独占责任，第三行表达借用。若调用方要把已有 unique_ptr 交给 install，必须显式移动，使交接在调用点可见。

只读业务函数一般不需要接受 `const unique_ptr<T>&`，因为它不关心调用者如何拥有 T。借用 const T& 往往更通用。确实要检查或替换拥有者时，再让接口接触包装类型。

## 3. get、reset、release 的差异

| 操作 | 含义 | 责任变化 |
| --- | --- | --- |
| `get()` | 得到目标裸指针 | 不变化，只借用 |
| `reset()` | 销毁当前目标并变空 | 放弃旧责任 |
| `reset(newPointer)` | 销毁旧目标，接管新目标 | 替换责任 |
| `release()` | 返回目标并变空 | 转交给外部，自己不销毁 |
| `std::move(owner)` | 允许目标操作搬走拥有者 | 是否转移取决于后续操作 |

表中的成员函数描述 unique_ptr 的接口，不能推导所有自定义资源类都完全一致。

`delete owner.get();` 会让 owner 留着一个已被删除的地址，之后再次销毁；`owner.reset(owner.get());` 同样可能形成悬空拥有者。release 后忘了接管，则变成泄漏。

## 4. make_unique 和自定义删除器

优先写 `std::make_unique<T>(arguments)`，将分配与建立所有者放在一个清楚的表达式里。在较早的语言规则及复杂表达式中，它也避免裸 new 后尚未接管的异常窗口。

C 库资源不能一律 delete。例如 FILE* 应交给 fclose，可以用删除器：

```cpp
struct FileCloser {
    void operator()(std::FILE* file) const noexcept {
        if (file != nullptr) {
            std::fclose(file);
        }
    }
};

using OwnedFile = std::unique_ptr<std::FILE, FileCloser>;
```

这是需要 `<cstdio>`、`<memory>` 的定义片段。删除器是类型的一部分，可能影响包装大小；不能把“unique_ptr 一定等大于裸指针”当成通用保证。

## 5. shared_ptr 为什么需要控制块

shared_ptr 通常关联目标指针及控制块。控制块记录强弱计数、删除器等信息，最后一个强所有者释放时销毁目标；若还有 weak_ptr，控制块仍需保留，供弱引用判断目标是否过期。

```text
shared_ptr A ─┐
              ├─ 控制块 ── 管理目标对象
shared_ptr B ─┘
weak_ptr W ───── 控制块（观察，不增加强计数）
```

拷贝 A 得到 B，是共享同一个控制块；从 A.get() 重新构造另一个 shared_ptr，则通常创建第二个控制块。两个控制块都以为自己负责 delete，会造成重复销毁。

make_shared 通常将对象与控制块合并分配，减少分配次数。存在长期弱引用时，对象虽已析构，合并分配的整块存储可能仍要等控制块释放；这对特别大的对象值得留意。

## 6. 完整示例：弱引用能观察，但不能保活

```cpp title="shared_lifetime.cpp"
#include <iostream>
#include <memory>

class Connection {
public:
    explicit Connection(int identifier) : identifier_(identifier) {
        std::cout << "open " << identifier_ << '\n';
    }

    ~Connection() {
        std::cout << "close " << identifier_ << '\n';
    }

    int identifier() const {
        return identifier_;
    }

private:
    int identifier_;
};

int main() {
    std::weak_ptr<Connection> observer;

    {
        auto owner = std::make_shared<Connection>(7);
        observer = owner;

        {
            auto secondOwner = owner;
            owner.reset();
            auto borrowedOwner = observer.lock();
            std::cout << "alive " << borrowedOwner->identifier() << '\n';
        }

        std::cout << "owner scope continues\n";
    }

    std::cout << std::boolalpha
              << "expired " << observer.expired() << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic shared_lifetime.cpp -o shared_lifetime
./shared_lifetime
```

输出：

```text
open 7
alive 7
close 7
owner scope continues
expired true
```

owner.reset 后，secondOwner 仍保活；lock() 成功时又得到一个强所有者。内层结束时这些强所有者依次释放，Connection 随最后一份强持有消失而析构，即便外层作用域尚未结束。

因此对象寿命不等于“最早那个 shared_ptr 变量的作用域”。

## 7. weak_ptr 的正确使用必须一步取得强所有者

```cpp
if (auto connection = observer.lock()) {
    use(*connection);
}
```

这是调用片段，use 代表同步业务处理。connection 在整个 if 体内保活，目标不会仅因其他所有者释放而消失。

先 expired() 再依赖某个裸指针访问是错误协议：检查与访问之间，其他线程可能释放最后强引用。expired 适合观测，lock 才负责原子地尝试获得强持有。

lock 保证目标生命周期，不保证目标成员的并发访问安全。如果 use 修改共享状态，仍需该类型自己的锁或线程约束。

## 8. 循环引用的根因和修复位置

A 强持有 B、B 强持有 A 时，外部强引用归零后，两者内部各留一份强计数。没有 GC 来遍历这种引用图并发现“虽然互相可达，但外部不可达”。

修复不是随便把一条边改 weak，而是明确主从关系：Session 拥有 Connection，Connection 只回看 Session，那么反向回调边通常可弱化。若业务真的要求平等共享，可能需要显式 shutdown/断连协议。

对象互相不直接引用也可能成环：对象持有任务队列，队列里的 lambda 强捕获该对象。排查时必须把回调对象也画进图。

## 9. enable_shared_from_this 解决哪个问题

当一个已由 shared_ptr 管理的对象在成员函数里需要交出强引用，不能 `shared_ptr<T>(this)`，因为这通常制造独立控制块。

继承 enable_shared_from_this<T> 后，通过 shared_from_this() 取得关联原控制块的强引用。但它要求对象已经被正确接管，构造函数里调用通常还太早，可能抛 bad_weak_ptr。

C++17 的 weak_from_this() 可取得对应弱引用；如果在构造阶段取到的是空弱引用，保存这份空值也不会在后来神奇地绑定所有者。应在建立 shared_ptr 后完成需要回调引用的初始化。

## 10. shared_ptr 的线程安全有三层

| 层次 | 保证 |
| --- | --- |
| 不同 shared_ptr 对象共享控制块 | 引用计数操作可并发进行 |
| 多线程读写同一个 shared_ptr 变量 | 需要同步，或使用对应原子操作 |
| 多线程访问目标 T 的成员 | 由 T 自己保证线程安全 |

两个线程分别持有副本，各自 reset 通常没问题；同一个成员指针被一线程赋值、另一线程读取，则不能仅依靠控制块安全。

use_count() 只是瞬时观察，不应写成“等于 1 就可以无锁修改目标”。别的线程可能立即取得新引用，或者存在不经过 shared_ptr 计数的借用。

## 11. 多态删除和别名构造的边界

unique_ptr<Base> 默认经 Base* delete，需要符合虚析构等规则。shared_ptr 的删除行为由建立控制块时保存的删除器与类型决定；从 make_shared<Derived>() 转成 shared_ptr<Base> 可保留正确的 Derived 删除行为。不能因此忽略接口基类的销毁设计。

shared_ptr 还支持别名构造：保活某个拥有对象，却让 get() 指向其中成员。此时“get 指向哪里”和“控制块负责销毁什么”并不相同。阅读复杂封装时，应回到控制块建立点确认真正拥有关系。

## 12. 应用到 Android Native

对于普通 STL 对象优先按独占、共享、借用选择类型；遇到 android::RefBase 则沿 sp/wp 协议，不要将两套计数机制混合接管同一对象。

比如 Surface 类成员保存某个 sp，说明存在强持有；把它的 get() 存进异步闭包并没有保存这份强持有。反过来，随意强捕获也可能让系统资源长时间无法释放。

标准库控制块和观察语义见 [util.smartptr.shared](https://eel.is/c++draft/util.smartptr.shared)；unique_ptr 的独占语义见 [unique.ptr](https://eel.is/c++draft/unique.ptr)。
