# 类、继承、虚函数与接口

Binder 接口、HAL、listener 和渲染后端经常通过基类指针访问实现类。要读懂这种代码，必须同时知道名字查找由哪个类型决定、虚调用最终落到哪个实现，以及销毁时按哪条路径清理资源。

Java 的很多实例方法默认参与动态分派；C++ 默认并非如此。本篇从这个差异展开，代码使用 C++17。

## 1. 静态类型与动态类型

如果 `GpuRenderer` 继承 Renderer，那么 `Renderer& renderer = gpu;` 中 renderer 的静态类型是 Renderer&，它引用对象的动态类型是 GpuRenderer。

编译器根据静态类型判断哪些名字可以调用、有哪些重载、访问控制是否允许；对于选中的虚函数，再由运行时对象决定最终覆写实现。

这两个步骤不能互相替代。基类没有某个方法时，编译器不会因为“对象实际上是子类”就允许调用。

## 2. public 继承表达接口替换

public 继承表示派生类可按基类接口使用。Base* 可以指向 Derived 的基类子对象；Derived 则要维持基类契约。

private/protected 继承改变转换与访问规则，不等于 Java 的 extends 加访问修饰符。只为复用一个成员或几个实现函数，组合通常更清晰。

多态本身不要求堆分配：一个栈上的 Derived 也能通过 Base& 虚调用。动态分派和动态存储期是两件事。

## 3. 完整程序：虚调用、非虚调用和默认参数

```cpp title="virtual_dispatch.cpp"
#include <iostream>
#include <memory>

class Renderer {
public:
    virtual ~Renderer() {
        std::cout << "~Renderer\n";
    }

    virtual const char* backend() const {
        return "base";
    }

    void describe() const {
        std::cout << "Renderer::describe\n";
    }

    virtual void draw(int quality = 1) const {
        std::cout << "base draw " << quality << '\n';
    }
};

class GpuRenderer final : public Renderer {
public:
    ~GpuRenderer() override {
        std::cout << "~GpuRenderer\n";
    }

    const char* backend() const override {
        return "gpu";
    }

    void describe() const {
        std::cout << "GpuRenderer::describe\n";
    }

    void draw(int quality = 2) const override {
        std::cout << "gpu draw " << quality << '\n';
    }
};

int main() {
    std::unique_ptr<Renderer> renderer = std::make_unique<GpuRenderer>();

    std::cout << renderer->backend() << '\n';
    renderer->describe();
    renderer->draw();
}
```

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic virtual_dispatch.cpp -o virtual_dispatch
./virtual_dispatch
```

输出：

```text
gpu
Renderer::describe
gpu draw 1
~GpuRenderer
~Renderer
```

backend 是虚函数，动态分派到 GpuRenderer；describe 非虚，按静态 Renderer 类型选中基类实现。

draw 最值得注意：函数体动态分派到子类，但默认参数在调用处按静态声明确定，因此参数是 1。设计虚接口时最好避免在派生覆写中提供不同默认参数，否则调用行为很容易超出读者直觉。

析构先走派生，再走基类，保证两层资源清理。

## 4. override 是编译器帮你审查签名

派生类写 `void draw()`，基类却声明 `void draw() const`，它们不是同一个覆写签名。少写 const 可能导致你以为重写成功，实际却隐藏了名字。

标 override 后，编译器会拒绝这种不匹配。派生类即便不重复写 virtual，正确覆写的函数仍然是虚函数；override 的价值是验证意图，不是开启虚分派。

final 可以放在类上阻止继续派生，也可以放在虚函数上阻止继续覆写。它表达设计边界，优化效果依赖实现和上下文。

## 5. 名字隐藏不等于虚覆写

基类有 `void resize(int);` 和 `void resize(int, int);`，派生类声明了一个同名 resize，可能隐藏基类整组重载。调用失败不一定是参数不支持，而可能是名字查找停在派生类。

可在派生类中用 `using Base::resize;` 把基类重载带入候选集。对复杂 AOSP 继承层次，应先确认找到哪个声明，再分析 overload resolution，而不是只 grep 到同名函数体。

## 6. 虚析构的精确适用条件

当对象将通过基类指针 delete，或交给默认删除器的 unique_ptr<Base> 销毁时，通常需要基类具有可访问的 virtual 析构函数。否则删除一个真实 Derived 会发生未定义行为。

不能把规则扩大成“所有带虚函数的类都必须 public virtual 析构”。另一种合法设计是 protected non-virtual 析构，明确禁止外部经基类指针销毁，只让受控派生路径负责。这类接口需要整体的所有权协议。

shared_ptr 还保存建立控制块时的删除行为，不能仅看变量当前模板参数推断 delete 类型；但这不应成为绕开清楚析构设计的理由。

## 7. 构造和析构期间为什么不调用最派生版本

基类构造时，派生部分尚未完成初始化；基类析构时，派生部分可能已经清理。因此这两个阶段的虚调用只按当前正在构造/析构的层次分派。

若基类构造函数调用虚方法，希望子类读自己成员完成初始化，设计已经依赖了不存在的不变量。纯虚调用在这些场景还会造成严重问题。

可把需要完整对象的步骤放在构造完成后的显式 start/init，但必须防止对象在初始化前被发布给其他线程。多一个方法并不自动消除状态顺序问题。

## 8. 对象切片：按值接口会丢失派生部分

```cpp
void record(Renderer renderer);
```

如果允许实例化 Renderer，将 Derived 按值传给此函数，会构造一个新的 Renderer 子对象值，派生部分被切掉。函数内动态类型已经是 Renderer，虚函数不再“记得来源是 GPU”。

多态参数通常应采用 Base&、Base* 或拥有指针。vector<Base> 保存 Base 值，不适合保存一组不同派生实现；vector<unique_ptr<Base>> 或其他明确的多态所有者更合适。

抽象基类的纯虚接口还能在编译期阻止某些切片，因为抽象 Base 不能实例化。

## 9. vtable 是理解工具，不是标准规定布局

主流 ABI 常用虚表和对象内的虚表指针实现分派。这个模型有助于理解间接调用、对象大小增加和指针调整，但 C++ 标准不承诺字段布局一定如此。

多继承时，Base* 可能指向对象中间的基类子对象，而不是最派生对象起始地址。因此不要随意把不同基类指针转成整数再假设它们相同，也不要用 reinterpret_cast 替代语言提供的继承转换。

dynamic_cast 对多态对象提供运行时类型检查；Android 模块是否启用 RTTI 由构建决定。代码阅读应确认实际配置和接口约定。

## 10. Binder 接口中的继承如何读

Android 16 的 `frameworks/native/libs/binder/include/binder/IInterface.h` 中可看到 IInterface 及 BnInterface/BpInterface 等模板的关系。

大体上，业务接口说明可调用方法；Bn 一侧将本地 Binder 对象与接口实现衔接；Bp 一侧将接口调用转向远端 Binder 句柄。模板参数表示它们服务的业务接口，不能只按类名推断“所有 Bn 都有完全相同的事务逻辑”。

沿一个方法读取时，先定位业务接口虚声明，再找服务实现 override，最后找 Proxy 如何编码、Stub 如何解码。这正好对应前面静态契约与动态实现的区别。

## 11. 组合与继承在锁和生命周期上的差异

如果 Listener 继承了多个带状态的基类，各基类可能拥有自己的 mutex、引用协议和销毁约束。一个简单回调就可能跨越多个隐含前置条件。

组合将这些依赖显示为成员，更容易画出拥有关系；继承则适合明确可替换的抽象。选择方式应依据契约，而不是仅因为“代码能少写几行”。

虚函数还可能调用未知实现。因此持锁调用一个外部可覆写方法，应像持锁调用任意回调一样审查重入风险。
