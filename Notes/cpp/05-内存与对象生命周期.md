# 内存与对象生命周期

Java 变量通常持有对象引用，C++ 的变量则可以直接就是对象本身。`Frame frame;` 在当前位置构造一个 Frame；`Frame* frame;` 只声明一个指针。分不清这两件事，会进一步误解传值、析构、容器和智能指针。

本篇从对象、存储和初始化分别建立模型。代码使用 C++17，后续章节的 RAII 与移动语义都依赖这些基础。

## 1. 变量名、存储空间和对象生命周期

“有一块地址”不等于“这里有一个活着的对象”。存储空间描述字节区域；对象生命周期描述某种类型的对象从何时起、到何时止可以按该类型合法使用。

多数普通对象在初始化完成后进入生命周期，类对象的构造/析构期间另有专门访问规则。析构与内存释放也不同：析构执行资源清理，释放存储则把那块空间交还分配器。普通 delete 表达式把两者组合起来。

| 写法 | 实际建立的东西 | 结束方式 |
| --- | --- | --- |
| `Frame frame;` | 一个局部 Frame 对象 | 作用域退出时析构 |
| `Frame* pointer = nullptr;` | 一个局部指针对象 | 指针退出作用域，不会销毁任何 Frame |
| `new Frame` | 动态存储上的 Frame，并返回指针 | 匹配的 delete 或所有者管理 |
| `std::make_unique<Frame>()` | Frame 加独占所有者 | 所有者释放时销毁 Frame |

“栈上”和“堆上”是有用的实现直觉，但标准讨论的是自动、静态、线程和动态存储期；优化器不保证每个局部对象都真的占用一个栈槽。

## 2. 和 Java 初始化规则最不同的地方

Java 的对象字段有默认零值；C++ 普通局部基础类型不普遍享受这一点。以下是语法片段：

```cpp
int uninitialized;
int zero{};
int width = 640;
```

在 C++17 中读取第一项的未初始化值是不合法的，不能期待编译器、系统或 Debug 构建自动清零。`int zero{};` 明确进行零初始化。

类类型执行什么初始化还取决于其构造函数。例如 `std::string text;` 会调用默认构造函数，得到空字符串，不能将它与未初始化的 int 等同。

统一用花括号也不是“所有歧义都消失”：它会优先参与 initializer_list 重载选择。例如 vector 的 `{3, 7}` 是两个元素，而 `(3, 7)` 是三个值为 7 的元素。

## 3. 构造函数负责建立不变量

一个对象应在公开可用前满足约定。例如缓冲区的宽高不能是随机数；一个成员引用必须绑定有效目标；一个只读 ID 必须有确定值。

```cpp
class Dimensions {
public:
    Dimensions(int width, int height)
        : width_(width), height_(height) {}

    int width() const { return width_; }
    int height() const { return height_; }

private:
    int width_;
    int height_;
};
```

初始化列表在函数体之前执行。将 `width_ = width;` 放进函数体是赋值，不是初始化。对于 string，前者可能先默认构造再赋值；对于 const 成员和引用成员，根本不能以函数体赋值替代初始化。

C++11 起可以用成员默认初始化器，例如 `int width_ = 0;`。某个构造函数显式初始化 width_ 时，以该构造函数的初始化列表为准。

## 4. 构造和析构顺序：完整观察程序

将代码保存为 lifecycle.cpp：

```cpp title="lifecycle.cpp"
#include <iostream>
#include <string>
#include <utility>

class Trace {
public:
    explicit Trace(std::string name) : name_(std::move(name)) {
        std::cout << "construct " << name_ << '\n';
    }

    ~Trace() {
        std::cout << "destroy " << name_ << '\n';
    }

private:
    std::string name_;
};

class Session {
public:
    Session() : connection_("connection"), cache_("cache") {
        std::cout << "Session body\n";
    }

    ~Session() {
        std::cout << "~Session body\n";
    }

private:
    Trace connection_;
    Trace cache_;
};

int main() {
    Trace outer("outer");
    {
        Session session;
        std::cout << "work\n";
    }
    std::cout << "after block\n";
}
```

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic lifecycle.cpp -o lifecycle
./lifecycle
```

输出为：

```text
construct outer
construct connection
construct cache
Session body
work
~Session body
destroy cache
destroy connection
after block
destroy outer
```

Session 的成员先构造，函数体后执行；析构时先执行 Session 的析构函数体，再按反向顺序析构成员。局部 Session 离开内层作用域就销毁，outer 一直活到 main 结束。

更一般的顺序是：虚基类、直接基类、按声明顺序排列的非静态成员、构造函数体。析构做相反方向的清理。

**成员声明顺序决定初始化顺序。** 即使把 cache_ 写在初始化列表前面，也不会改变其声明在 connection_ 后面的事实。一个成员初始化依赖另一个尚未初始化成员，是难以肉眼发现的错误。

## 5. 构造函数失败时谁负责清理

构造函数抛异常，表示最外层对象没有构造成功，它自己的析构函数不会执行。但已经成功构造的基类和成员会析构。这解释了为什么资源应尽量放入 RAII 成员中：它们能在半途失败时自动清理。

如果在构造函数体中裸 new 一块内存，随后另一操作抛异常，只有一个普通指针成员并不能替你 delete。换成 unique_ptr 成员后，成员自身的析构可完成回收。

Android 平台模块通常对异常有特定配置。禁用异常的代码常用工厂或显式初始化结果报告失败。即便没有异常，成员初始化顺序和正常退出时的析构规则仍成立。

## 6. 临时对象与“借用不能转移寿命”

```cpp
const std::string& label = std::string("surface");
```

这里直接绑定会将临时 string 的生命周期延长到 label 的生命周期结束。这是特定语法规则，不是“只要有引用，对象就活着”。

函数参数是很重要的例外场景：

```cpp
const std::string& identity(const std::string& value) {
    return value;
}
```

若调用 `const auto& label = identity(std::string("surface"));`，临时对象只活到初始化表达式结束，也就是该分号处。返回引用不会再次延长它。后续访问 label 已经悬空。

将引用塞进另一对象、复制一个引用、用 lambda 捕获引用，都不是新的所有权。分析这种代码时应沿数据来源追到真正的对象，而非停留在引用变量名称上。

## 7. 静态和线程存储期

函数内 `static` 对象在第一次执行到定义时初始化。C++11 起，其初始化具有并发保护；对象构造完成后的普通方法调用并不会自动加锁。

不同编译单元的非局部静态对象存在初始化顺序问题。若某个全局构造函数访问另一文件尚未初始化的对象，就可能出错。进程退出时相反的析构顺序也会暴露依赖问题。

`thread_local` 给每个线程独立实例，适合线程上下文，但它的销毁发生在线程退出，不等于进程退出。生命周期比普通局部变量长，也可能长于某些外部依赖。

## 8. Java GC 经验不能直接迁移的原因

Java 的可达性通常决定对象是否可回收；C++ 局部对象的作用域、拥有者操作或引用计数决定销毁时机。一个引用变量依然存在，并不能阻止其目标被别的代码销毁。

另一面，C++ 可以依赖确定析构清理锁和句柄，而 Java 往往要用 try-with-resources 明确资源作用域。两者都要求区分“托管对象存活”与“操作系统资源是否已关闭”。

## 9. Android 对象为什么常有 init/start

构造一个 Native 服务对象，通常只完成成员与基本状态初始化。注册 Binder、启动线程、链接依赖可能放在单独方法里，因为这些操作可能失败、可能回调当前对象，或需要对象先被强引用持有。

这意味着要画出两条不同的线：

```text
语言生命周期：分配 → 构造 → 使用 → 析构 → 释放存储
服务状态：未连接 → 已初始化 → 已注册 → 运行 → 停止
```

服务运行失败不意味着 C++ 对象立即析构；对象尚存也不意味着业务处于可用状态。查看 start 返回值、停止状态和线程 join 位置，才能把两条线关联起来。
