# 锁：保护一组状态，而不是包住越多代码越安全

锁的目标是维护共享状态的不变量。先写清“哪些字段由哪把锁保护”，再决定临界区；持锁太少会产生数据竞争，持锁调用外部代码又可能死锁或发生重入。

## 1. 用 RAII 包装加锁和解锁

```cpp
std::mutex mutex;
{
    std::lock_guard<std::mutex> lock(mutex);
    // 临界区
} // 自动解锁
```

- `lock_guard`：简单作用域锁，不能手工提前解锁。
- `unique_lock`：可延迟加锁、提前解锁，是条件变量常用搭档。
- `scoped_lock`：可一次获取多把锁，并使用避免死锁的加锁策略。

不要手写 `lock()` 后在多个 return 分支逐个 `unlock()`；异常或新分支很容易漏掉清理。

## 2. 完整示例：同时锁两个账户完成转账

```cpp title="lock_demo.cpp"
#include <iostream>
#include <mutex>
#include <thread>

struct Account {
    std::mutex mutex;
    int balance;
};

bool transfer(Account& from, Account& to, int amount) {
    if (&from == &to || amount <= 0) return false;

    std::scoped_lock lock(from.mutex, to.mutex);
    if (from.balance < amount) return false;
    from.balance -= amount;
    to.balance += amount;
    return true;
}

int main() {
    Account first{{}, 1000};
    Account second{{}, 1000};

    std::thread a([&] { for (int i = 0; i < 100; ++i) transfer(first, second, 1); });
    std::thread b([&] { for (int i = 0; i < 100; ++i) transfer(second, first, 1); });
    a.join();
    b.join();

    std::cout << first.balance + second.balance << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -pthread lock_demo.cpp -o lock_demo
./lock_demo
```

输出始终是 `2000`。余额检查和两个余额的更新处于同一临界区，`scoped_lock` 避免两个线程用相反顺序各拿一把锁。

## 3. 条件变量必须搭配状态条件

```cpp
std::unique_lock<std::mutex> lock(mutex);
ready.wait(lock, [&] { return closed || !queue.empty(); });
```

通知不是永久保存的消息，等待还可能无理由返回，所以总要在锁保护下检查谓词。修改条件状态、通知等待者、关闭时唤醒全部线程要形成一个完整协议。

## 4. 常见死锁来源

- 两条路径用不同顺序获取多把锁。
- 持锁等待线程 `join`，而被等待线程正要获取同一把锁。
- 持锁调用回调、虚函数或同步 IPC，对方重入当前对象。
- 析构最后一份智能指针时仍持锁，而析构又进入需要该锁的代码。

修复时画出“线程持有什么、正在等待什么”的等待图。缩短临界区有帮助，但不能破坏状态原子性。规则细节可查 C++17 工作草案 N4659 的 `[thread.mutex]`、`[thread.lock]` 和 `[thread.condition]`。
