指定 App 强制窗口大小和位置方案

目标

在 framework 层按包名或组件名把指定 Activity/Task 强制启动为 freeform 窗口，并应用固定窗口 bounds。该方案用于源码实验和模拟器验证，不新增公开 SDK API。

实现概览

入口选择在 LaunchParamsController，因为新建 task、复用已有 task、从 launcher/adb/应用内启动 Activity 的路径都会先计算 launch params，再创建或选择 root task，最后由 layoutTask() 应用 bounds。

本方案新增：

  • ForceAppBoundsConfig：解析全局 setting force_app_bounds。
  • ForceAppBoundsLaunchParamsModifier：命中配置后输出 WINDOWING_MODE_FREEFORM 和指定 Rect。
  • LaunchParamsController.registerDefaultModifiers()：把强制策略注册在 modifier 链尾，使其优先于已有 desktop/freeform 默认策略。
  • ActivityRecord.supportsMultiWindowInDisplayArea() 和 TaskFragment.supportsMultiWindowInDisplayArea()：对命中强制规则的非 resizeable app 放行，避免被 validateWindowingMode() 退回 fullscreen。
  • development/samples/ForceBoundsDemo：实验 APK，用公开 API 显示当前窗口 metrics。

153 if (values.length != 4) {

155 + entryForLog);
156 return null;
157 }
158

162 final int right = Integer.parseInt(values[2].trim());
163 final int bottom = Integer.parseInt(values[3].trim());

165 Slog.w(TAG, "Ignoring empty bounds in " + SETTING_KEY + " entry: "

116 private void fitBoundsInDisplayArea(@NonNull TaskDisplayArea displayArea,

修改点选择原因

  • 选择 LaunchParamsController 作为入口，是因为它覆盖新建 task、复用已有 task、launcher 启动、adb 启动和应用内启动等主要路径；在这里输出 windowingMode + bounds，比在单个启动入口做特判更完整。
  • 单独新增 ForceAppBoundsLaunchParamsModifier，而不是直接改 TaskLaunchParamsModifier，是为了把实验策略和系统已有桌面模式、默认 freeform 策略隔离开，后续删除或产品化都更清晰。
  • registerDefaultModifiers() 中把强制 modifier 注册在最后，是因为 LaunchParamsController 计算时按反向顺序遍历 modifier；强制规则需要优先于已有 desktop/freeform 默认策略。
  • ActivityRecord 和 TaskFragment 都要补放行，是因为系统既可能在 Activity 级校验，也可能在已有 Task/TaskFragment 路径校验。如果只改 launch params，非 resizeable App 仍可能被 validateWindowingMode() 或相关校验退回 fullscreen。
  • bounds 会先限制到 TaskDisplayArea stable bounds 内，是为了避免错误配置把窗口放到状态栏、导航栏或屏幕外；最终 bounds 还会继续受系统最小 task 尺寸约束。
  • 配置暂放在 Settings.Global，是为了源码实验阶段方便通过 adb shell settings put 快速调整，不需要新增公开 API、系统服务接口或独立配置文件。

配置格式

配置写入 Settings.Global.force_app_bounds：

adb shell settings put global force_app_bounds 'com.android.forceboundsdemo=80,120,800,900'

支持多个规则，用分号分隔：

adb shell settings put global force_app_bounds \
  'com.android.forceboundsdemo=80,120,800,900;com.example.app/.MainActivity=40,80,760,720'

规则格式：

  • 包级规则：package.name=left,top,right,bottom
  • 组件级规则：package.name/.Activity=left,top,right,bottom
  • 坐标单位：物理像素，right/bottom 是 Rect 右下边界，不是宽高。
  • 组件级规则优先于包级规则。
  • bounds 会被限制到目标 TaskDisplayArea 的 stable bounds 内，避免窗口完全跑出屏幕。
  • 实际窗口仍会经过系统最小可调整 task 尺寸约束；如果配置宽高低于当前设备最小值，最终 bounds 可能被放大。

清除配置：

adb shell settings delete global force_app_bounds

模拟器验证步骤

1编译 framework 和 demo：

source build/envsetup.sh
lunch sdk_phone64_x86_64 trunk_staging userdebug
m services ForceBoundsDemo

如果当前 shell 已经 lunch 过同一产品，可以只执行 m services ForceBoundsDemo。

2刷入或重启到包含新 framework 的镜像。只改 framework 时通常需要重新生成并启动整机镜像；如果设备支持快速替换 system/framework，也可以按本地调试习惯处理。

3确认 freeform 支持打开：

adb shell settings put global enable_freeform_support 1
adb reboot

goldfish provisioning 默认会打开该开关；如果已打开，可以跳过这一步。

4安装 demo APK：

adb install -r out/target/product/emu64x/system/app/ForceBoundsDemo/ForceBoundsDemo.apk

5写入强制 bounds 并启动：

adb shell settings put global force_app_bounds 'com.android.forceboundsdemo=80,120,800,900'
adb shell am force-stop com.android.forceboundsdemo
adb shell am start -n com.android.forceboundsdemo/.MainActivity

6观察：

adb shell dumpsys activity activities | grep -A20 com.android.forceboundsdemo
adb logcat -d | grep ForceAppBounds

demo 页面里的 WindowMetrics bounds 和 Decor size/location 可用于和配置值交叉核对。

行为说明

  • 命中规则后，启动参数被改为 freeform + 指定 bounds。
  • 如果目标窗口当前是已有 task，ActivityStarter 会先用 launch params 选择/迁移 root task，再由 layoutTask() 应用 bounds。
  • 如果系统没有开启 freeform window management，规则会被忽略并打印 ForceAppBounds warning。
  • home/recents 等非 standard activity type 不应用该规则。
  • 该实现不改 Shell 拖拽/吸附/最大化策略；如果用户后续手动拖动窗口，后续启动或复用 task 时会再次按配置覆盖。

约束与产品化建议

当前实现是实验方案，适合验证“按 App 固定 freeform 启动大小和位置”这条链路。产品化时建议：

  • 把 force_app_bounds 从裸字符串迁移为受权限保护的 DeviceConfig、Settings provider 表或 OEM 配置文件。
  • 增加 userId/displayId 维度，避免多用户和多显示器场景互相影响。
  • 给配置更新加缓存和 ContentObserver，减少频繁解析 setting 的成本。
  • 明确和桌面模式、任务持久化、Shell 窗口拖拽/最大化策略之间的优先级。
  • 增加 CTS/GTS 或内部集成测试，覆盖新启动、复用 task、非 resizeable app、配置删除和非法配置。
